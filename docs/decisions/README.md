## Purpose

Use this log to keep architectural decisions concise and durable. Each decision
should record the choice, rationale, consequences, status, and review trigger.

## Current decisions

| ID | Decision | Status | Rationale | Consequence | Review trigger |
| --- | --- | --- | --- | --- | --- |
| D-001 | Use Packer, Terraform, and Ansible as the core workflow | Accepted | Keeps image build, provisioning, and configuration clearly separated | Tool boundaries stay explicit | If one tool is replaced or merged |
| D-002 | Keep the repository public and commit examples only | Accepted | Enables sharing without publishing secrets | Users must create private operational copies | If secret handling or distribution model changes |
| D-003 | Use Proxmox as the chosen virtualization platform | Accepted; clarified by D-030 | Keeps the infrastructure implementation concrete without making every service choice part of the architecture | Proxmox-specific code and guides stay explicit; other hypervisors are not selectable implementations in this kit | If a second virtualization platform is implemented |
| D-004 | Treat this repository as a curated upstream reference, not the destination for operational changes | Accepted | Reduces accidental publication of live configuration and secrets | Users continue development in private forks, mirrors, or local copies | If the repository ownership or collaboration model changes |
| D-005 | Prefer secure defaults and segmented network design | Accepted | Reduces accidental overexposure and drift | Some environments require explicit exceptions | If operational needs require broader trust |
| D-006 | Use modular deployment building blocks with logical compute and storage abstractions | Accepted | Keeps deployment interfaces reusable, separates compute size from storage placement and capacity, and hides platform-specific details behind modules and mappings | Environment inputs stay stable while implementation details remain replaceable | If the module interface model or workload abstractions change |
| D-007 | Use an enterprise-grade Linux operating system for managed general-purpose instances | Accepted | Gives managed workloads a durable and predictable operating system strategy without coupling the architecture to one vendor, distribution, version, or image source | Platform guides can document the current implementation while the architectural decision remains portable | If the baseline guest operating system strategy changes |
| D-008 | Keep identity foundation deployment separate from Vault foundation deployment | Accepted | The repository starts from clean Proxmox and network prerequisites only, so the first foundation stage should not assume shared services such as DNS, PKI, or Vault already exist | Early automation stays focused on the first managed identity foundation layer, and Vault keeps its own Terraform environment, inventory, and playbook once those prerequisites are ready | If the foundation scope or early shared-service order becomes the repository default |
| D-009 | Use an edge load balancer in `external_edge` for early north-south traffic and keep a separate internal cluster proxy for later Kubernetes ingress | Accepted | Keeps the early infrastructure edge separate from later cluster-native ingress while preserving a stable network and service model as the platform grows | Architecture and service guides should treat the `external_edge` edge load balancer as an early prerequisite; implementation choices stay in the foundation setup docs rather than the architecture model | If the edge placement model or the later cluster ingress model changes |
| D-010 | Keep the identity foundation path focused on the default authority design and treat Windows or AD support as a secondary extension | Accepted | Keeps the default path focused on identity, DNS, PKI, and secret-platform prerequisites while avoiding Windows-specific complexity in the first deployment | Identity foundation docs should stay focused on the default authority path; Windows support should have its own path; the current reference direction is FreeIPA as the primary authority with Samba AD as the Windows support extension | If the primary authority model or the Windows support approach changes |
| D-011 | Use `FreeIPA` in `identity` plus a split PKI with an issuing CA in `cryptography` and an offline root CA in `ceremony` for the default identity foundation | Accepted | Keeps the first authority path clear and Linux-native while separating online identity and issuing services from offline root-CA custody | Foundation examples should default to `2` `FreeIPA` hosts in `identity`, `1` issuing CA host in `cryptography`, and an optional offline root CA host in `ceremony`; later HSM backing remains an upgrade path, not a day-one requirement | If the authority platform, PKI split, or HSM-default model changes |
| D-012 | Treat identity, PKI, secrets, and observability as shared services that can be deployed here or consumed from existing infrastructure | Accepted | Keeps the repository modular for clean builds, existing environments, isolated labs, and multi-project use | Reader paths live under `docs/paths/shared-services/` when they create or consume the shared-service backbone; later paths should not deploy duplicate identity or secret systems unless isolation requires it | If shared services become mandatory or a different service ownership model is chosen |
| D-013 | Use OpenTelemetry as the observability backbone with dedicated backends for live health, metrics, traces, logs, and archive | Accepted | Keeps telemetry routing generic while allowing practical reference implementations | The observability path should use generic VM roles and place product choices in service variables, tags, and guide text; sources should send through telemetry gateways or security collectors instead of writing directly to backends | If the observability stack or routing model changes |
| D-014 | Use `FreeIPA` with constrained Kerberos and hardware-backed user identity proof | Accepted | Keeps the first domain recoverable while defining a clear security model: hardware keys prove operator identity, Kerberos provides internal SSO, SSH should use short-lived OpenSSH certificates or non-delegatable credentials, and hosts are treated as compromisable | Identity docs should keep passwords as the default bootstrap path, prefer Kerberos and PKI for long-term trust, avoid credential delegation, and document YubiKey, compatible hardware-key, and SSH certificate hardening separately | If the default authentication model changes or hardware-backed auth becomes mandatory |
| D-015 | Divide repositories into Tier 0, Tier 1, and Tier 2 by potential impact | Accepted; clarified by D-023 | Makes privilege, ownership, and recovery responsibility explicit | Tier 0 owns the highest-impact control systems and must recover without Tier 1 or Tier 2; network placement is a separate decision | If a service gains authority over a lower-numbered tier |
| D-016 | Treat this upstream as a deployment kit that generates private downstream repositories | Accepted | Keeps public guidance and reusable automation separate from environment-owned operational state | Tooling generates `<prefix>-tier-0`, `<prefix>-tier-1`, `<prefix>-tier-2`, `<prefix>-shared`, and `<prefix>-architecture` repositories with generated and owned paths | If the repository returns to a single operational-tree model |
| D-017 | Make Tier 0 the first recovery target with a dedicated cluster and GitOps control path | Accepted | The operating model needs a recoverable bootstrap and control foundation before broader shared services or workloads | Tier 0 docs define the Day 0/1 bootstrap plane and Day 2 GitOps model; the current reference implementation can use Proxmox, Talos, Flux, and Kubernetes for those roles | If Tier 0 is implemented without Kubernetes or if another bootstrap substrate is chosen |
| D-018 | Keep one Terraform/Ansible inventory contract per tier, with common helpers and stateless data in shared | Accepted; clarified by D-028 | Separates operational ownership while retaining one mechanism for names, IPs, and environment overlays | Three tier-owned inventories, resource modules, and state roots; no live inventory in shared; inventory applications remain Day 2 consumers | If inventory ownership, recovery inputs, or cross-tier orchestration changes |
| D-019 | Draw security layers horizontally and tiers vertically; name the rightmost layer Control | Accepted | Separates network protection from impact and ownership without confusing the Control layer with the management network | Edge is leftmost; Tier 2 is above Tier 1 above Tier 0; diagrams distinguish classification, network access, and offline custody handoffs | If layer responsibilities or the tier/network model changes |
| D-020 | Assign networks and firewall zones directly to tier/layer cells | Superseded by D-023 | Originally attempted to combine ownership and firewall design in one naming scheme | Required tier-prefixed zones and treated all Tier 0 as offline; this coupled independent decisions and made naming harder to follow | Retained as decision history, not current guidance |
| D-021 | Tier 0 owns all VM template lifecycles; first publication is Day 0-1 | Accepted | Managed VMs need approved templates before any control cluster or hosted job system exists | Local publication and recovery work first; optional Day 2 CD reuses Tier 0 state and implementation; see [Template lifecycle](../platforms/proxmox/template-lifecycle.md) | If distribution, custody isolation, or cluster bootstrap ownership changes |
| D-022 | Mirror generated ownership in the source tree | Accepted | Tier inputs and reusable automation should be located without reading generator mappings | `tier-0/`, `tier-1/`, `tier-2/`, and `shared/` are the payload sources; generation copies them and adjusts sibling paths | If generated ownership or payload boundaries change |
| D-023 | Separate impact tiers from network protection and keep naming conventions short | Accepted | Makes it easy to do right without encoding several independent models into names | Tier 0 may be connected; isolate custody separately. Use purpose-named networks and zones; the project worksheet records VM names, tags, VMID ranges, and VLAN conventions, not a second inventory | If privileges, exposure, or policy require reclassification or finer segmentation |
| D-024 | Tier 0 owns hardware-facing control across all tiers | Accepted | Physical hosts, virtualization, storage, and network administration can affect every workload | Keep tier-local workload definitions and state roots; infrastructure execution authority remains Tier 0 | If delegated permissions or state ownership change |
| D-025 | Enable future workload self-service through Tier 0 GitOps | Accepted design; not implemented | Tier 2 users should request VM creation and updates without administering infrastructure | Tier 0 owns request policy, protected execution, and independent operation; see [Infrastructure control](../architecture/infrastructure-control.md) | Before choosing a controller, request schema, authorization, or state handoff |
| D-026 | Treat VM node placement as creation-only | Accepted | Proxmox HA and operator migrations must not cause Terraform to move VMs back | VM hardware remains managed; source-template node is explicit for cross-node clones; LXC is excluded. See [cluster placement](../platforms/proxmox/cluster-ha.md#terraform-against-the-cluster) | If Terraform-driven migration is required or provider refresh behavior changes |
| D-027 | Keep one shared consumer template catalog, with Tier 0-owned publication | Accepted | Consumers need approved IDs and titles without repeating recipes or reading Tier 0 state | Shared references are project-owned; helpers load them before tier overrides. See [template catalog](../platforms/proxmox/template-catalog.md) | If multi-cluster distribution or automated promotion changes the contract |
| D-028 | Keep Terraform resources and all inventories tier-owned | Accepted | Makes resource ownership visible and independently maintainable | Shared contains scripts, roles/tasks, and stateless data only; guest modules are intentionally copied per tier, while sizes and image references remain single-source. See [automation layout](../reference/infrastructure-automation-layout.md#tier-owned-automation) | If lifecycle ownership or delegated execution changes |
| D-029 | Organize Terraform as deployments and modules | Accepted | Makes the design readable from the tree without deployment-specific layout exceptions | Keep independent state and the inventory contract; see the [design map](../reference/infrastructure-automation-layout.md#terraform-structure) | If lifecycle boundaries or root composition change |
| D-030 | Name capabilities independently of implementation products | Accepted | Makes goals and ownership durable when a service or node OS changes | Kubernetes is the cluster goal; Talos is the current implementation example. Public cluster entry points use Kubernetes names, while provider-specific code and existing state remain explicit. Proxmox stays the chosen hypervisor. See [cluster choices](../platforms/kubernetes/README.md#implementation-choice) | Before adding another node OS, installer, or service implementation |

## Review triggers

Review relevant decisions when changes affect:

- repository structure
- trust boundaries
- secret handling
- supported platforms
- automation workflow ownership
