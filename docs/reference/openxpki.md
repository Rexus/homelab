## Local inputs

Source: Tier 0 [issuer.yml.example](../../tier-0/ansible/group_vars/issuer.yml.example).
Pass its ignored local copy explicitly with `--ansible-vars`; sibling `group_vars`
files are not automatically discovered by every inventory/playbook combination.

| Input | Contract |
| --- | --- |
| `openxpki_deployment_id` | Stable local identity for this runtime installation |
| `openxpki_configuration_src`, `openxpki_configuration_sha256` | Absolute controller archive path and independently reviewed SHA-256 |
| `openxpki_package_versions` | Exact versions for `libopenxpki-perl`, `openxpki-cgi-session-driver`, `openxpki-i18n`; matched to configuration/schema |
| `openxpki_repository_key_sha256` | Independently verified signing-key checksum; HTTPS and APT signature checks remain enabled |
| `openxpki_data_mount`, `openxpki_data_uuid` | Dedicated prepared filesystem, not the root disk |
| `openxpki_admin_networks` | IPv4 CIDRs allowed to use the authenticated TLS portal |
| `openxpki_publication_networks` | Consumer CIDRs allowed to fetch public certificate/CRL objects |
| `openxpki_realm` | Single production realm name in the supplied bundle |
| `openxpki_initialize_database` | Explicit one-time permission to import schemas into an empty database |
| `openxpki_activate_runtime` | Explicit permission to enable the signing services after signer/custody preparation; token import follows |
| `openxpki_issuer_fingerprint` | Independently recorded colon-separated SHA-256 fingerprint of the public issuer certificate |
| `openxpki_required_state_paths` | Existing files/directories beneath the data mount required by the signer and DataVault |

| Controller environment variable | Purpose |
| --- | --- |
| `OPENXPKI_DATABASE_PASSWORD` | Local backend database password, at least 32 characters |
| `OPENXPKI_SESSION_PASSWORD` | Separate frontend-session database password, at least 32 characters |
| `OPENXPKI_SESSION_SECRET` | Stable frontend session encryption secret, at least 32 characters |
| `OPENXPKI_TLS_CERT_FILE` | Portal full chain with the portal DNS SAN |
| `OPENXPKI_TLS_KEY_FILE` | Matching independently prepared private key |

Secret-only encrypted overrides are supported during Ansible-only execution.
Do not put these secrets, configuration archives, private keys or CA state in Git.

## Storage

Prepare and persist mounts before package installation; the role does not format,
partition, encrypt or relocate a database. For `/srv/openxpki`, use this layout:

| Path | Ownership and recovery content |
| --- | --- |
| `/srv/openxpki` | Dedicated filesystem with the recorded UUID, writable with sufficient free space |
| `/srv/openxpki/mysql` → `/var/lib/mysql` | Persisted bind mount on the same filesystem; prepare before MariaDB installation |
| `/srv/openxpki/configuration/<sha256>` | Reviewed production configuration and matched schema artifacts |
| `/srv/openxpki/keys/` | Separately prepared signer/provider/DataVault material; never generated by reconciliation |
| `/srv/openxpki/identity/issuer.pem` | Approved public issuer certificate, checked before activation |
| `/srv/openxpki/public/` | Public certificates and CRLs only; never private keys, database exports or configuration |
| `deployment.json`, `schema-initialized` | Runtime binding and schema-completion receipt; restore with the application set |

Service drop-ins require the data and database mounts. Losing them stops the
dependent units instead of allowing an empty OS-directory database at the next boot.
An application-consistent database backup and independent key recovery remain
necessary; copying a live data directory is not a qualified CA backup.

## Production configuration bundle

The [software PKI builder](../deployment/stage-2-trust/procedures/software-pki.md)
supplies a pinned native policy starting point. Its input example defines
suffixes, independent password-hash identities and publication URLs. Review and
qualify the resulting artifact with the selected package/schema combination.
Set `openxpki_managed_cli: true` for this bundle's private administrative key
and CRL timer; keep it false for externally supplied bundles with their own
qualified CLI/scheduling arrangements.

Use a reviewed production configuration derived from the matched upstream
[configuration repository][1], not its unmodified demonstration realm. The archive
contains these paths at its root, with all imports/symlinks resolved within the bundle:

| Archive path | Required content |
| --- | --- |
| `config.d/system/` | Native backend settings, exactly the selected production realm, protected CLI and logging configuration |
| `config.d/realm/<realm>/` | Complete crypto/provider settings, independent local authentication, roles/ACLs, workflows and restrictive leaf profiles |
| `client.d/` | Matching current frontend/service configuration, Unix sockets and independent local authentication |
| `log.conf` | Product logging configuration; CA events must reach the already-tested Stage 1 forwarding path |
| `schemas/backend.sql`, `schemas/frontend.sql` | Unmodified MariaDB schemas from the same approved configuration/package combination |

The role supplies only backend database credentials and frontend database/session
settings as native YAML overlays. Other policy remains project-owned. Configuration
must use `/run/openxpkid/openxpkid.sock` and `/run/openxpki-clientd/openxpki-clientd.sock`,
publish certificates/CRLs beneath the data mount's `public/` directory, and reference
separately prepared signing state. Preserve OpenXPKI's DataVault secret/token with
the database; it is not supplied by HashiCorp Vault. [1]

Remove demo realms, test accounts, anonymous portal login, wildcard certificate
authentication, example subjects/URLs and CA-capable ordinary enrollment profiles.
The initial role enforces exactly one non-demo realm, `LocalPassword` and private
`System` handlers, and `LocalPassword`/`_System` stacks. Additional authentication
methods require a separate qualified configuration change.
Qualify requester/approver separation and denied requests before real issuance.
This is a required policy review, not a claim that YAML parsing proves security.

Package the reviewed tree as a gzip tar archive on the controller, record its SHA-256,
and retain an encrypted offline recovery copy. It contains secrets even though the
database/session overlays are supplied separately. `sampleconfig.sh` is not executed.
The complete reviewed realm/policy bundle must be supplied; policy is not inferred
from inventory or downloaded from a moving upstream branch during deployment.

The software builder additionally includes secret `cli.pem` at archive root.
It is copied to protected signing storage only when managed CLI is explicitly enabled.
Treat it as a privileged custody credential, not a leaf or portal account.

## Reconciliation and activation

The deployment binding pins configuration checksum, package versions and secret
digest. Routine reruns reconcile that same set; changes require a rehearsed upgrade
or credential-rotation procedure. Do not delete a binding or initialization receipt
to bypass it. Failed schema imports or missing tables require explicit recovery.

Installation leaves signing daemons disabled until activation. Activation checks
required local state and the expected unexpired CA certificate, then enables the
native services and checks the local API. Token creation/import, provider-specific
permissions, actual signing, CRL freshness, forwarding, backup and restore acceptance
are separate controlled operations. No ACME bridge, OCSP responder or application HA
is implied by this runtime installer.
